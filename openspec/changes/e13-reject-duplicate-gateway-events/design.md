# Design

## Context

See proposal.md for motivation; the behavior is in the spec delta. Current state, verified in the code:

**How handlers reach the gateway runtime**

- `#[handlers]` turns each `#[subscribe_message(EVENT)]` method into a `DiscoveredHandler { class_name, method_name,
  kind: HandlerKind::WsMessage { event, call, enhancers } }`, pushed in declaration order
  (`crates/corvis-macros/src/handlers.rs:237-323`). `EVENT` is any expression, not only a literal
  (`args.first().cloned()`, `handlers.rs:239`; `String::from(#event)`, `:295`), so constants such as
  `#[subscribe_message(events::JOIN)]` work.
- `DiscoveredHandler` and `HandlerKind::WsMessage` are in `crates/corvis/src/discovery.rs:71-75` and `:66`.
- A type has a single `HandlersProvider` impl (`discovery.rs:78`, generated by `#[handlers]`), so all handlers of a
  gateway come from one `#[handlers]` block; a second block on the same type is a conflicting-impl compile error.

**`build_gateways` (`crates/corvis/src/websockets.rs:544-598`)**

- For each provider with a gateway hook it resolves the gateway's enhancers, creates `let mut handlers =
  HashMap::new();` (`:560`) and, for every `HandlerKind::WsMessage` (`:562-563`), logs `"{gateway} subscribed to the
  \"{event}\" message"` (`:564`), resolves the handler's enhancers and inserts it with
  `handlers.insert(event, Arc::new(compiled))` (`:580`). A second handler for the same event replaces the first; the
  return value of `insert` is ignored.
- Only after the loop does it register the server in `SERVERS` (`:584-585`), call `after_init` (`:586-588`) and
  insert the `GatewayRuntime` under the gateway path (`:589-594`).
- It returns `Result<_, DiError>`; `DiError::Other(String)` displays the string as is
  (`crates/corvis/src/di/error.rs:31-32`). `init()` calls it after `build_router` and `build_middleware`
  (`crates/corvis/src/application.rs:399-402`) and propagates the error with `?`; `listen` and
  `listen_in_background` call `init()` through `bind` (`application.rs:476-477`).
- Incoming frames look up `gateway.handlers.get(&event)` (`websockets.rs:941`): exact, case-sensitive match.

**Precedent**

- Duplicate scheduler names make `init()` fail with `"{kind} with the given name ({name}) already exists. Ignored."`
  (`crates/corvis/src/modules/schedule/mod.rs:286-289`), tested in `crates/corvis/tests/schedule.rs:288-305`
  (`duplicate_names_fail_the_bootstrap`, which calls `app.init().await.unwrap_err()`).

**Original framework (source read from its repository, master branch, on 2026-11-08)**

- `packages/websockets/gateway-metadata-explorer.ts` collects message handlers from
  `metadataScanner.getAllMethodNames(prototype)` (declaration order) and does not check for repeated message names;
  `web-sockets-controller.ts` logs one "subscribed to the ... message" line per handler and passes them all to the
  adapter. No warning or error for duplicates anywhere.
- `packages/platform-ws/adapters/ws-adapter.ts`, `bindMessageHandlers`: `handlers.forEach(handler =>
  handlersMap.set(handler.message, handler))`, then `handlersMap.get(message.event)`. The last handler wins; the
  earlier one never runs. Corvis behaves exactly like this today.
- `packages/platform-socket.io/adapters/io-adapter.ts`, `bindMessageHandlers`: one `fromEvent(socket, message)`
  subscription per handler, so every handler for the event runs, and each may call the ack.

**Tests and examples**

- `crates/corvis/tests/websockets.rs` covers gateways (`gateway_roundtrip`, line 61;
  `gateway_guards_run_with_a_ws_execution_context`, line 305); nothing covers duplicates.
- `examples/cats-app/src/chat.rs` (`join`, `message`, `ping`) and `examples/tertulia/src/chat/chat_gateway.rs`
  (`join`, `leave`, `message`, `typing`, `clear`, `rooms`) have no duplicate events. The port apps have no gateways.

**Related changes**

- #116 (`e13-exception-filters-and-global-guards-on-gateways`) rewrites the handler loop of `build_gateways` (global
  enhancers, filters); #27 (`e1-route-posture-for-websockets-and-sse`, design decision 1) splits it into
  `compile_gateways` (before the posture check) and `start_gateways` (servers and hooks). Both leave the
  `handlers.insert(event, ..)` behavior unchanged; #27 lists this issue as out of scope.

## Goals / Non-Goals

**Goals:**
- No `#[subscribe_message]` handler, and none of its guards, can be replaced silently.
- The error says which gateway, which event and which two methods, so the fix is obvious.

**Non-Goals:**
- Duplicate gateway paths, HTTP route conflicts and compile-time detection (proposal.md, Out of scope).
- Several handlers per event (the socket.io fan-out).

## Decisions

1. **Reject duplicates at startup instead of matching the original.** The original has no single behavior: `ws`
   keeps the last handler, socket.io runs all of them, and neither warns. Matching `ws` (today's behavior) keeps a
   silent shadowing that can hide an unguarded handler behind a guarded one in the source; matching socket.io is not
   possible with the `{ event, data }` protocol without sending two replies to one frame. In both originals a
   duplicate is a mistake (dead code or a double reply), so refusing to start costs a migrating user one edit and
   follows the project rule "security over parity".
   Alternatives considered: (a) keep last-wins and log a warning. Rejected: a warning in a startup log is easy to
   miss, and the guard bypass remains. (b) Keep the first handler. Rejected: still silent, and different from both
   originals.
2. **Check in `build_gateways`, not in the macro.** Before inserting, `build_gateways` looks the event up in the map;
   if it is there, it returns `DiError::Other` with the message from the spec, using the earlier handler's method name
   and the current one. To have the earlier method name, `CompiledWsHandler` keeps its `target` (whose `name` is the
   method name, `websockets.rs:576-577`), so no new field is needed. The check and the error happen before the
   `subscribed` log line of the duplicate, and before `SERVERS`, `after_init` and the runtime insert of that gateway.
   Alternative considered: a compile-time check in `#[handlers]`. Rejected as the only check: event names can be
   constants or expressions, which the macro cannot compare. A macro check for literal duplicates could be added on
   top later (Out of scope), but the startup check covers every case with one implementation.
3. **Report the first collision only.** The error names the first two methods that share an event, in declaration
   order, and stops, like the scheduler check. Listing every collision would need a second pass for a case that is
   rare and quick to fix.
   Alternative considered: collect all duplicates of all gateways into one error. Rejected as more code for little
   gain; revisit if users ask.
4. **Exact comparison of event names.** The map key is the event string, compared the same way frames are
   dispatched (`websockets.rs:941`), so `"message"` and `"Message"` stay two events. Different gateways keep their own
   maps, so the same event on two gateways is fine.
5. **Placement relative to #116 and #27.** The check is a few lines next to `handlers.insert`. If #27 has split the
   function, it goes into `compile_gateways`, so the posture check and the hooks never see a shadowed handler. Whichever
   lands later rebases; no API changes either way.

## Risks / Trade-offs

- [An application migrated from a socket.io gateway relied on two handlers running for one event] → it fails at
  startup with both method names; the migration guide explains merging them into one handler. Corvis has no socket.io
  adapter yet (#35), so such apps do not run on Corvis today anyway.
- [Startup fails after other gateways already ran their `after_init`] → `build_gateways` handles gateways one by one,
  so a gateway processed earlier may have run its hook. Same as any other `init()` error after hooks; the duplicate's
  own gateway runs nothing. #27's split into compile and start phases removes this as a side effect.
- [No differential test against the original] → the behavior intentionally diverges and a startup error has no Node
  counterpart to compare; the original's behavior is recorded in Context with file and function names, and the
  migration guide documents the divergence. See Open questions.

## Open questions

1. **Divergence from the original.** Confirm rejecting duplicates (Decision 1) rather than matching the `ws` adapter's
   last-wins behavior with a warning.
2. **socket.io adapter (#35).** socket.io runs every handler for an event. Should Corvis keep rejecting duplicates when
   the socket.io adapter lands (proposed: yes, for the same guard-shadowing reason), or allow them only there? To be
   settled in #35.
3. **Differential test.** The project asks for a differential test when an original library exists. Here the change
   diverges on purpose; confirm that recording the original's source behavior (Context) and documenting the divergence
   is enough.

## Review notes (2026-11-08)

Decisions taken for the open questions so the change can start; the maintainer can still overrule them in review:

- Diverging from the original is confirmed: duplicates fail startup instead of "last one wins" with a warning, under
  the security-over-parity rule (a guarded handler silently shadowed by an unguarded one).
- The socket.io adapter (#35) keeps rejecting duplicates; that change inherits this check.
- No differential test: the original's behavior is documented in the docs page and in design.md.
- The folder was renamed to `e13-reject-duplicate-gateway-events` (issue #125).
