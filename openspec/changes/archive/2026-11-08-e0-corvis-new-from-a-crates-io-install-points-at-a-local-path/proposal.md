# Proposal

Implements [randygil/corvis#121](https://github.com/randygil/corvis/issues/121) (epic
[#1](https://github.com/randygil/corvis/issues/1)).

## Why

Without options, `corvis new` writes the generated project's framework dependency as a path to the `crates/corvis`
folder of the checkout the CLI was compiled from (`crates/corvis-cli/src/main.rs:150-154`, built from
`env!("CARGO_MANIFEST_DIR")` at compile time). A CLI installed with `cargo install corvis-cli` is compiled inside the
Cargo registry cache (`~/.cargo/registry/src/<index>/corvis-cli-<version>/`), where `../corvis` does not exist, so
every project it generates points at a missing folder and does not build. The CLI cannot be released (#11 and later)
while its default output is broken for anyone who did not build it from a clone.

## What Changes

- **Default dependency:** with no `--corvis-path`, no `--corvis-version` and no `CORVIS_PATH`, the generated
  `Cargo.toml` gets `corvis = { version = "<CLI version>" }`, where the version is the CLI's own
  `env!("CARGO_PKG_VERSION")` (`0.1.0` today). The CLI and the framework crates are released together with the same
  version (the exact pins of #10), so the CLI's version is the framework version its templates were written for.
- **Local checkout stays available, opt-in:** the existing `--corvis-path <dir>` flag and `CORVIS_PATH` environment
  variable keep writing `path = "<dir>"`. No new flag. The compile-time fallback to the CLI's own checkout is removed.
- **Precedence made explicit:** a flag beats the environment variable; passing both `--corvis-path` and
  `--corvis-version` is an error (today `--corvis-version` silently wins); an empty `CORVIS_PATH` counts as unset.
- **Hint for contributors:** when the default version is written and the checkout the CLI was compiled from still
  exists on disk, `corvis new` prints one `NOTE` line with the `--corvis-path` value that would use it. It never
  switches to the path by itself. When the path comes from `CORVIS_PATH`, a `NOTE` line says so.
- `corvis --help` describes the default and the `CORVIS_PATH` variable.
- Tests: unit tests of the dependency selection and integration tests of the generated `Cargo.toml` (default version,
  flag, environment variable, precedence, conflicting flags).
- Docs (English and Spanish): `docs/cli/overview.md` ("Framework dependency"), `docs/cli/usages.md` (`corvis new`
  options), `docs/first-steps.md` (dependency table and tip), and the root `README.md` sentence on `corvis new`
  options. Until the first release, they tell readers to use `CORVIS_PATH` or `--corvis-path`.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `cli/new`: adds the framework dependency rules (published version by default, local path only on request) and
  adjusts the "Generated project starts" scenario so it names a dependency that resolves.

## Impact

- Code: `crates/corvis-cli/src/main.rs` (`corvis_dependency`, `cmd_new`, help text, unit tests) and
  `crates/corvis-cli/tests/` (integration tests). `templates.rs` keeps its `__CORVIS_DEP__` placeholder unchanged.
- No framework runtime crate changes; the examples, `scripts/smoke-examples.mjs` and CI are unaffected (none of them
  builds a project generated by `corvis new`; the examples use workspace path dependencies).
- Behavior change for contributors who run a CLI built from their clone without options: they now get a version
  requirement and must set `CORVIS_PATH` (once, in their shell profile) or pass `--corvis-path`. The `NOTE` line tells
  them how.
- Before a release of the framework crates with the CLI's version exists on crates.io, a project generated with the
  defaults does not resolve its dependency (`failed to select a version for the requirement corvis = "^0.1.0"`).
  #11 reserves the names with `0.0.x` releases, which a `0.1.0` requirement does not match. See design.md, decision 5
  and open question 1.
- The VS Code extension's "Corvis: New Project" runs `corvis new <name>` without options
  (`editors/vscode/src/generate.ts:159`), so it gets the version requirement too (Out of scope).

## Out of scope

- Publishing anything (#11 and the first real release need explicit approval).
- The VS Code extension passing `CORVIS_PATH` when it runs the CLI from a framework checkout (`cargo run
  --manifest-path ...`): follow-up issue for the extension.
- Adding other framework crates (`corvis-orm`, `corvis-swagger`) to the generated project; when a template adds one,
  it uses the same dependency source (design.md, decision 4).
- The "not on crates.io yet" sentences and path dependency samples in other docs pages (`docs/deployment.md:18`,
  `docs/openapi/introduction.md:17-22`, `docs/data/corvis-orm.md:17-18`): they stay true until the first release.
- Packaging metadata of `corvis-cli` (#10).
