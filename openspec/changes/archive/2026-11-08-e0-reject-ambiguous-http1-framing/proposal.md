# Proposal

Implements [randygil/corvis#146](https://github.com/randygil/corvis/issues/146) (epic
[#1](https://github.com/randygil/corvis/issues/1)). Decided in [#8](https://github.com/randygil/corvis/issues/8)
(`openspec/changes/archive/2026-11-08-e0-decide-compatible-vs-strict-mode/`, design.md decisions 2 and 3): option C,
secure defaults per behavior, with `insecure_http_parser` as the opt-out for the wire format only.

> **Status: approved (2026-11-08).** The maintainer approved the framing check in `TimedIo` (design.md decision 1,
> option 3); see design.md, "Review notes".

## Why

Corvis parses HTTP/1 with hyper 1.12.0 and httparse 1.10.1. A raw-socket probe (`node-probe/`, this folder) shows four
inputs that Node 24 (llhttp 9.3.0) answers with `400` and Corvis accepts. A proxy in front of Corvis can read the
same bytes differently, which is the shape of a request smuggling bug:

1. Bare LF as a line ending in the request line or header lines, including a head ended by `CRLF LF` or `LF CRLF`.
2. Whitespace after a chunk size (`2 \r\n`, `2\t\r\n`, `2 ;a=b\r\n`).
3. `Content-Length` together with `Transfer-Encoding: chunked`: hyper decodes the body as chunked and closes the
   connection after the response (allowed by RFC 9112 section 6.3, so lower risk).
4. Bare LF inside the trailer section. Confirmed: hyper ends the trailer section only on `CRLF CRLF`. With
   `0\r\nX-A: b\n\nGARBAGE\r\n\r\n` it keeps `X-A: b`, drops `GARBAGE` and serves the next pipelined request. A proxy
   that ends the message at `\n\n` would forward `GARBAGE...` as a new request.

hyper and httparse have no option to reject any of them (design.md, Context). The issue asked to choose between an
upstream option and a fork. This change compares both with a third approach, a framing check in Corvis' own accept
loop, and recommends that one.

## What Changes

- **Behavior change (default):** the four inputs above are answered with `400` and the connection is closed. A
  request that follows on the same connection (pipelined) is never processed.
- New `ServerOptions::insecure_http_parser(bool)` (default `false`), named after Node's `insecureHTTPParser`. `true`
  restores today's behavior for those four inputs, and only for them. Inputs that hyper already rejects stay rejected.
  Corvis logs a warning at startup when it is on.
- Inputs that stay as they are, now pinned by tests: an empty line (CRLF or bare LF) before the request line is
  ignored, as in Node; leading zeros in chunk sizes are accepted; bare CR in a header, a chunk size over 64 bits, bare
  LF in the chunked framing and LF in a chunk extension are still rejected.
- A differential test that replays the probe's requests against Corvis and compares statuses with Node's, regression
  tests for each rejected input, pipelining tests, and an opt-out test.
- A property test that runs the new check and hyper on the same generated byte streams and fails if they disagree on
  where a request ends.
- Docs (EN + ES): `docs/security/http-parsing.md` (status column, the opt-out, the new rows) and the `ServerOptions`
  list in `docs/http/performance.md`.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `http/request-parsing`: adds requirements for CRLF-only line endings in the request head and the trailer section,
  for the chunk-size line without whitespace, for rejecting `Content-Length` with `Transfer-Encoding`, for closing
  the connection after such a rejection, and for the `insecure_http_parser` opt-out.

## Impact

- Code: `crates/corvis/src/server.rs` (`ServerOptions`, `TimedIo::poll_read`, `serve`) and a new private module for
  the HTTP/1 framing check under `crates/corvis/src/`. No new dependency. hyper and httparse are not changed.
- Public API: one new method, `ServerOptions::insecure_http_parser`.
- Tests: `crates/corvis/tests/transport_security.rs` (or a new `http1_framing.rs` test binary), a fixture recorded
  from the probe under `crates/corvis/tests/fixtures/`, unit and property tests next to the new module.
- Docs: `docs/security/http-parsing.md`, `docs/es/security/http-parsing.md`, `docs/http/performance.md`,
  `docs/es/http/performance.md`.
- Clients: requests built by HTTP libraries (Node's `http`, browsers, curl, reqwest, proxies) always use CRLF and one
  length header, so they are not affected. Hand-written clients or old devices that send bare LF get `400` and need
  the opt-out.
- Parity: apidiff sends requests with `node:http`, which always writes CRLF, never sends whitespace after a chunk size
  or bare LF in trailers, and never sends both length headers. The three port apps should keep 0 differences. The
  remaining risk is a framing check that rejects a valid request it should pass (design.md, Risks); apidiff exercises
  that path on every request.
- Performance: one extra scan over request heads and chunked framing lines, plus a copy of incomplete heads. Measured
  by task 5.4.

## Out of scope

- Upstream patches to httparse or hyper. design.md decision 1 describes what they would need. Opening issues or PRs
  upstream is tracked as a separate issue (#148).
- Two more inputs where Node is stricter than Corvis: two identical `Content-Length` headers and
  `Transfer-Encoding: chunked, chunked`. Both have one possible reading, so they are not ambiguous framing. Listed in
  the docs; the review decided not to reject them in this change.
- `HTTP/1.0` with `Transfer-Encoding`: hyper answers `400`, Node accepts it. Corvis keeps being stricter.
- HTTP/2 (h2c): binary framing, not affected. Whether h2c stays on by default is issue #144.
- Header size and header count limits: unchanged (`431`).
