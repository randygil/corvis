### 1. Current state of Corvis

- There is no queue code. `docs/application/queues.md` (and `docs/es/application/queues.md`) has front matter
  `status: unavailable` and says "Corvis does not yet include a job queue module", suggesting `EventEmitter` or a
  hand-made provider instead.
- There is no Redis client: `crates/corvis/Cargo.toml` lists no Redis crate, and `Cargo.lock` has no `redis` or
  `fred` package. The optional features are `jwt` and `websockets` (`crates/corvis/Cargo.toml:45-48`), which is the
  precedent for an optional, heavier subsystem.
- None of the three port apps (consi, facten, houseplan, under `corvis-tests/nest/`) depends on `bullmq`, `bull`,
  `ioredis` or `redis` (checked every `package.json` outside `node_modules`). The parity check does not exercise
  queues; queue parity must come from the new interop tests.
- Method-level handlers are discovered through a closed enum, `HandlerKind` (`crates/corvis/src/discovery.rs:61-67`:
  `Event`, `Cron`, `Interval`, `Timeout`, `WsMessage`), generated by `#[handlers]`
  (`crates/corvis-macros/src/handlers.rs:97`, which recognises `on_event`, `cron`, `interval`, `timeout`,
  `subscribe_message`). `crate::modules::register_handlers` (`crates/corvis/src/modules/mod.rs:19-62`) wires them,
  `mount_scheduler` runs between `on_module_init` and `on_application_bootstrap`
  (`crates/corvis/src/application.rs:349-357`), and `stop_scheduler` runs after `on_module_destroy` and before
  `before_application_shutdown` (`crates/corvis/src/application.rs:507-517`, call at line 513). Workers need the
  same three moments: register, start, stop.
- `CorvisFactory::create_application_context` (`crates/corvis/src/application.rs:64-68`) only calls the init hooks;
  handler discovery happens in `init()` (`application.rs:418-419`). A standalone worker process therefore depends on
  change `e13-standalone-application-context-runs-events-and-scheduled` (#16), which makes the standalone context
  register handlers.
- Dynamic modules follow one pattern: `ScheduleModule::for_root*` (`crates/corvis/src/modules/schedule/mod.rs:557-584`),
  `JwtModule::register` (`crates/corvis/src/jwt.rs:333`), `ConfigModule::for_root` (`crates/corvis/src/config.rs:275`)
  return a `DynamicModule` with value or factory providers. `#[injectable]` fields accept `#[inject("TOKEN")]`
  (`crates/corvis-macros/src/injectable.rs:31`), the base for `#[inject_queue("name")]`.
- Corvis's own cron engine is a port of the npm `cron` package (`crates/corvis/src/modules/schedule/mod.rs:1-2`), not
  of `cron-parser`, which is what BullMQ uses. It must not be reused for job schedulers (Decision 7).
- Tests against Node already follow two patterns: recorded oracles (`crates/corvis/tests/fixtures/res_express.oracle.mjs`
  writes `res_express.json`, read by `crates/corvis/tests/res.rs:116`) and live services gated by an environment
  variable with a loopback default (`CORVIS_ORM_PG`, `crates/corvis-orm/tests/common/pg.rs:3,11`; skipped when
  unreachable). Change `e0-ci-in-github-actions` adds a Postgres service container and a `_REQUIRED` switch
  (`openspec/changes/e0-ci-in-github-actions/design.md:89-90`). Queue interop needs a live Node process sharing a
  live Redis, so it follows the second pattern.

### 2. The BullMQ data model in Redis (Node BullMQ 6.7.2)

#### Keys

All keys of queue `<q>` are `<prefix>:<q>:<suffix>`, default prefix `bull` (`classes/queue-keys.js:2-37`). The base
keys built by `QueueKeys.getKeys`:

| Suffix | Type | Contents |
|---|---|---|
| `""` (`<prefix>:<q>:`) | prefix | job keys are this plus the job id |
| `wait` | list | ids ready to run, priority 0. Producers `LPUSH` (or `RPUSH` with `lifo`); workers `RPOPLPUSH wait active` (`commands/moveToActive-11.lua:74`) |
| `paused` | list | 5.x only: holds waiting ids while the queue is paused. 6.x keeps jobs in `wait` and only drains a leftover `paused` list on resume (`commands/pause-7.lua`) |
| `active` | list | ids being processed |
| `waiting-children` | sorted set | parents waiting for children (flows) |
| `prioritized` | sorted set | score `priority * 2^32 + (INCR pc) % 2^32` (`commands/includes/getPriorityScore.lua`); taken only when `wait` is empty (`moveToActive-11.lua:74-85`) |
| `pc` | string | priority counter |
| `delayed` | sorted set | score `(timestamp + delay) * 0x1000 + n`, with `n` (0–4095) keeping FIFO order inside one millisecond (`commands/includes/getDelayedScore.lua`) |
| `completed`, `failed` | sorted sets | score `finishedOn` (ms) (`commands/moveToFinished-14.lua:172`) |
| `id` | string | `INCR` counter for automatic job ids (`commands/addStandardJob-9.lua`) |
| `meta` | hash | `paused`, `concurrency` (global), `max`/`duration` (global rate limit), `opts.maxLenEvents` (default 10000), `version` = `bullmq:<version>` (`classes/queue.js:74-78`; `commands/includes/getQueueMetadata.lua`) |
| `events` | stream | the events of the queue, trimmed with `MAXLEN ~ opts.maxLenEvents` |
| `marker` | sorted set | wake-up marker: `ZADD marker 0 "0"` when a job becomes available, or the next delayed timestamp; workers block on `BZPOPMIN marker` (`commands/includes/addBaseMarkerIfNeeded.lua`; `classes/redis-queue-backend.js:1911`) |
| `stalled` | set | ids that were active at the last stalled check |
| `stalled-check` | string | `SET ... PX stalledInterval`: only one worker runs the stalled check per interval (`commands/moveStalledJobsToWait-9.lua:48`) |
| `limiter` | string | rate-limit counter, `PEXPIRE` = limiter duration (`commands/includes/prepareJobForProcessing.lua`) |
| `repeat` | sorted set + hashes | job schedulers: zset of scheduler ids by next run; hash `repeat:<schedulerId>` with `name`, pattern/every, `tz`, template `data`/`opts` (`commands/includes/storeJobScheduler.lua:65`) |
| `de` | prefix | deduplication keys `<prefix>:<q>:de:<id>` |

Keys derived from a job key `<prefix>:<q>:<jobId>`: `:lock` (string, value = worker token, `PX lockDuration`),
`:logs` (list), and for flows `:dependencies` (set of child job keys), `:processed` (hash child key → return value),
`:failed` (hash), `:unsuccessful` (sorted set). Metrics use `metrics:completed` / `metrics:failed` keys.

#### Job hash

`HMSET <prefix>:<q>:<jobId>` (`commands/includes/storeJob.lua`), then fields added by later scripts. The reader is
`rawToJobJson` (`classes/redis-queue-backend.js:2073-2099`):

| Field | Written by | Value |
|---|---|---|
| `name` | add | job name |
| `data` | add | `JSON.stringify(data)` |
| `opts` | add | JSON of the job options, with six keys abbreviated: `de` deduplication, `fpof` failParentOnFailure, `cpof` continueParentOnFailure, `idof` ignoreDependencyOnFailure, `kl` keepLogs, `rdof` removeDependencyOnFailure (`utils/index.js:90-97`) |
| `timestamp`, `delay`, `priority` | add | integers (ms, ms, 0–2^21-1) |
| `parentKey`, `parent` | add (flows) | parent job key; JSON `{id, queueKey}` |
| `rjk` | add (scheduler) | repeat (scheduler) key |
| `deid` | add | deduplication id |
| `processedOn`, `pb` | moveToActive | start time; worker name (`prepareJobForProcessing.lua`) |
| `ats` | moveToActive | attempts started (`HINCRBY`) |
| `atm` | finish/retry | attempts made (`HINCRBY` in `moveToFinished-14.lua`, `moveToDelayed-11.lua`, `retryJob-11.lua`); older data may have `attemptsMade` |
| `stc` | stalled check | stalled counter (`moveStalledJobsToWait-9.lua`) |
| `returnvalue` / `failedReason`, `finishedOn` | moveToFinished | JSON of the return value / error message; finish time |
| `stacktrace` | failure | JSON array of strings (`classes/job.js:945-950`, limited by `stackTraceLimit`) |
| `progress` | updateProgress | JSON number or object |
| `defa` | flows | deferred failure (a child failed) |

#### Scripts

Node 6.7.2 ships 64 Lua scripts (`commands/*.lua`, named `<name>-<numKeys>.lua`, with `includes/` resolved at build
time). Arguments are packed with msgpack and unpacked with `cmsgpack.unpack` (for example `addStandardJob-9.lua`:
`ARGV[1]` packed array, `ARGV[2]` JSON data, `ARGV[3]` packed options). Node loads them as custom commands named
`<name>:<version>` (`classes/redis-queue-backend.js:307-318`). Roles:

- Adding: `addStandardJob-9`, `addDelayedJob-6`, `addPrioritizedJob-9`, `addParentJob-6`.
- Processing: `moveToActive-11` (promote due delayed jobs, check pause/global concurrency/rate limit, take a job,
  set the lock, `ats += 1`, emit `active`), `extendLock-2` / `extendLocks-1`, `moveToFinished-14` (verify the lock
  token, set `returnvalue`/`failedReason` + `finishedOn`, `atm += 1`, `ZADD completed|failed`, apply
  `removeOnComplete`/`removeOnFail`, update the parent, emit `completed`/`failed`, optionally fetch the next job),
  `moveToDelayed-11` and `retryJob-11` (retries), `moveStalledJobsToWait-9`, `moveToWaitingChildren-7`.
- Queue management: `pause-7`, `drain-5`, `obliterate-2`, `cleanJobsInSet-3`, `promote-9`, `changeDelay-4`,
  `changePriority-7`, `removeJob-2`, `retryJob-11`, `reprocessJob-9`, `moveJobsToWait-8`, `updateData-1`,
  `updateProgress-3`, `addLog-2`.
- Reading: `getCounts-1`, `getRanges-1`, `getJobs-1`, `getState-8`, `getStateV2-8`, `isFinished-3`, `paginate-1`,
  `getMetrics-2`, `getRateLimitTtl-2`, `isMaxed-2`.
- Schedulers: `addJobScheduler-11`, `updateJobScheduler-12`, `removeJobScheduler-3`, `getJobScheduler-1`.
- Flows: `addParentJob-6`, `getDependencyCounts-4`, `removeChildDependency-1`, `removeUnprocessedChildren-2`,
  `releaseParentIfNoPendingDependencies-2`.
- `relay*-1` (14 scripts): BullMQ 6 relay feature, unrelated to jobs.

#### Job lifecycle

1. **Add** (`Queue.add` → `addStandardJob`/`addDelayedJob`/`addPrioritizedJob`). Without `jobId` the id is
   `INCR id`. With a `jobId` that already exists, nothing is written and the existing id is returned, with a
   `duplicated` event (`includes/handleDuplicatedJob.lua`). The job goes to `delayed` (delay > 0), `prioritized`
   (priority > 0) or `wait`; the stream gets `added` then `waiting` (or `delayed`); `marker` is set if the queue is
   not paused or at its global concurrency.
2. **Fetch.** A worker blocks on `BZPOPMIN marker` (up to `drainDelay`, default 5 s, capped at 10 s) and runs
   `moveToActive`, which first promotes delayed jobs whose time has come, then returns a rate-limit TTL, nothing
   (paused/maxed), a job, or the next delayed timestamp.
3. **Lock.** `<job>:lock` = worker token with `PX lockDuration` (default 30 000 ms). The worker renews it every
   `lockRenewTime` (default `lockDuration / 2`) with `extendLock(s)`, which also removes the id from `stalled`.
4. **Complete** → `moveToFinished` with target `completed`. **Fail** → the worker decides (`classes/job.js:445-460`,
   `shouldRetryJob`): if `attemptsMade + 1 < attempts`, the error is not an `UnrecoverableError` and
   `maxStartedAttempts` is not reached, compute the backoff; delay > 0 → `moveToDelayed`, delay 0 → `retryJob`
   (back to `wait`); a backoff of `-1` means "do not retry". Otherwise `moveToFinished` with target `failed`, plus
   a `retries-exhausted` event when attempts ran out.
5. **Backoff** (`classes/backoffs.js`): a number means `fixed`; `fixed` → `delay`; `exponential` →
   `round(2^(attemptsMade-1) * delay)`; optional `jitter` in [0, 1] randomises within `[delay*(1-jitter), delay]`;
   other types call the worker's `settings.backoffStrategy`.
6. **Stalled** (`moveStalledJobsToWait-9.lua`): every `stalledInterval` (default 30 000 ms) one worker reads
   `stalled`; each id there whose lock is gone is moved back to `wait` with `stc += 1` and a `stalled` event, or
   failed with `"job stalled more than allowable limit"` when `stc` exceeds `maxStalledCount` (default 1); then all
   current `active` ids are copied into `stalled`.
7. **Retention**: `removeOnComplete` / `removeOnFail` accept `true`, a count, or `{age, count}`; the default keeps
   every finished job.

Worker defaults (`classes/worker.js:40`): `concurrency: 1`, `lockDuration: 30000`, `maxStalledCount: 1`,
`stalledInterval: 30000`, `drainDelay: 5`, `maximumRateLimitDelay: 30000`, `runRetryDelay: 15000`, `autorun: true`.

#### Producer validation (`classes/job.js:897-942`, `classes/queue.js:178-179`)

Errors thrown before anything is written: `jobId` equal to `'0'` or starting with `'0:'`; a custom id that is an
integer ("Custom Id cannot be integers"); an id with `:` unless it has exactly three parts ("Custom Id cannot contain
:"); a float priority; a priority above 2 097 151; `sizeLimit` exceeded; more than one of the exclusive
parent-failure options; deduplication without `id` or together with a parent; the removed `debounce` option; backoff
`jitter` outside [0, 1].

#### Events stream

Every state change is an `XADD` to `<prefix>:<q>:events` with `event` and `jobId` plus fields per event, for example
`completed` with `returnvalue` and `prev: active`, `failed` with `failedReason` and `prev`
(`moveToFinished-14.lua:198`), `active` with `prev: waiting`, `progress` with `data`, `delayed` with `delay`,
`retries-exhausted` with `attemptsMade`, `stalled`, `drained`. `QueueEvents` reads it with a blocking `XREAD`
starting at `$` or `lastEventId` (`classes/queue-events.js:66`). Workers also emit local, in-process events.

#### Redis server versions

Node BullMQ requires Redis ≥ 5.0.0 and warns below 6.2.0 (`classes/redis-connection.js:623-624`). The official Rust
SDK requires Redis 6.2+ (or Valkey, Dragonfly) (`docs/gitbook/rust/introduction.md`).

### 3. What changed between BullMQ 5 and 6

From the migration guide and a script-by-script comparison of 5.81.5 and 6.7.2:

- Legacy repeatable jobs are removed (`Queue.add(..., { repeat })`, `getRepeatableJobs`, `removeRepeatable*`; scripts
  `addRepeatableJob-2`, `removeRepeatable-3`, `updateRepeatableJobMillis-1` are gone). "If v6 encounters legacy
  repeatable-job metadata, it raises an error". Job Schedulers (`upsertJobScheduler`) are the only repetition.
- Pause semantics: 5.81.5 adds jobs of a paused queue to `paused` (`addStandardJob-9.lua:108`,
  `getTargetQueueList`), and `pause-7` `RENAME`s `wait` ↔ `paused` (`pause-7.lua:5-6,24`). 6.7.2 keeps jobs in
  `wait`, decides with `HEXISTS meta paused` (`includes/isQueuePaused.lua`), and on resume moves a leftover `paused`
  list into `wait` in chunks of 7000. A 5.x `resume` while both lists have jobs would `RENAME paused wait` and
  overwrite `wait`: mixing 5.x and 6.x processes that pause/resume one queue can lose jobs.
- `debounce` option removed (deduplication only); flow children without `jobId` get UUIDs instead of `INCR` ids;
  `Queue.resume()` is async.
- Of the 46 scripts present in both versions, 22 differ once includes are resolved; `getCountsPerPriority`,
  `moveToDelayed` and `reprocessJob` changed their key count.

`@nestjs/bullmq` 12.0.1 accepts BullMQ 3–6, so the Node apps we migrate can be on either major. 6.0.0 is three months
old; most running apps are probably still on 5.x.

### 4. The official Rust SDK (`bullmq-official` 1.5.0)

- Same scripts. The published crate embeds `src/commands/*.lua` (`rust/src/scripts.rs`, `include_str!`). Comparing
  its 64 scripts with the `content` of Node 6.7.2's `scripts/*.js`: 63 are byte-identical; `getCounts-1` differs
  only because Node 6.7.2 added an optional delayed-cutoff argument. Against 5.81.5 only 25 are identical.
- Scripts run with `EVALSHA` and fall back to `EVAL` on `NOSCRIPT` (`rust/src/scripts.rs:34-46`).
- Coverage (`rust/FEATURE_PARITY.md`): Queue (add, add_bulk, pause/resume, drain, clean, obliterate, getters, counts,
  metrics, global concurrency and rate limit, deduplication), Worker (concurrency, stalled detection, lock renewal,
  retries with fixed/exponential/custom backoff, graceful `close(timeout_ms)`, rate limiter, progress,
  `CancellationToken`), `Job`, `FlowProducer`, Job Schedulers, cross-process `QueueEvents` over `XREAD BLOCK`, TLS,
  Redis Cluster. Missing: legacy repeatable jobs, Sentinel, telemetry, `Job.wait_until_finished`.
- Special processor outcomes mirror Node's errors: `Error::Unrecoverable`, `Error::Delayed`,
  `Error::WaitingChildren`, `Error::RateLimited` (`rust/src/error.rs:5-86`).
- Dependencies (crates.io, 1.5.0): `redis ^1.7.1` with `tokio-comp`, `connection-manager`, `cluster-async`,
  `script`, `tokio-rustls-comp`, `tls-rustls-webpki-roots`; `tokio ^1.53`; `croner ^4.0.1` (cron); `rmp-serde`;
  `chrono`, `chrono-tz ^0.10` (Corvis already uses `chrono-tz 0.10`); `sha1 ^0.11` (Corvis uses `sha1 0.10`, a
  duplicate in the tree); `uuid`; `tracing`. `rust-version = 1.85`, but `redis 1.x` needs 1.88. The local toolchain
  is 1.99 and the workspace sets no `rust-version`.
- Release cadence: 1.0 in July 2026, 1.5.0 on 2026-11-04, about two releases a week, released by semantic-release
  from commits tagged `[rust]` in the main repository.
- Known divergence found while reading: the crate writes `HSET meta library "bullmq-official:0.1.0"` (a stale
  constant, `rust/src/queue.rs:23,728-740`), while Node writes `version = "bullmq:6.7.2"` and
  `opts.maxLenEvents`. Node's `queue.getVersion()` returns `null` for a queue only the Rust SDK touched. No job
  behavior depends on it, but a state snapshot shows it.
- Cron: Node 6.7.2 computes the next run with `cron-parser 5.10.3`; the crate uses `croner`. Edge cases (seconds
  field, `L`/`W`/`#`, DST transitions, `tz`) can differ.

## Goals / Non-Goals

**Goals:**
- Pin down the Redis format Corvis queues must read and write, with a BullMQ version.
- Choose how to implement it in Rust and which Redis client to use, with evidence.
- Define the differential test that proves interop, so every follow-up can use it.
- Write the requirements each follow-up implements, and a plan per issue.

**Non-Goals:**
- Writing any code, attribute, docs page or CI job (#50–#57 do that).
- Choosing the final names of every public type: #50–#55 decide them in their own changes, within the shape given
  here.
- Compatibility with the original `bull` package or with BullMQ < 5.

## Decisions

### 1. Compatibility target: BullMQ 6.x data format, with a tested 5.x subset

Corvis queues read and write the BullMQ 6 Redis format (reference: Node BullMQ 6.7.2; the interop suite pins it and
bumps it on purpose). Against BullMQ 5.81.5 the supported subset is: add, process, retry, fail, delay, priority,
progress, events, flows, rate limiting. Not supported against 5.x: legacy repeatable jobs (6.x refuses them) and
pause/resume while 5.x processes share the queue (job-loss risk above). Docs (#57) state this.

- *Alternative: target 5.x.* Most apps today, but the official scripts and every future fix follow 6.x, and 5.x will
  stop getting releases. A 6.x worker reads jobs added by a 5.x producer (same job hash, same `wait`/`delayed`/
  `prioritized` encodings; resume drains a leftover `paused` list), which covers the common migration: Node producer
  on 5.x, new Corvis worker.
- *Alternative: support both formats.* Needs two script sets and version detection; the legacy repeat format is the
  main difference and BullMQ itself dropped it. Rejected.

### 2. Implementation: wrap the official `bullmq-official` crate

`corvis::queues` depends on `bullmq-official` (imported as `bullmq`) and adds what Corvis users need on top: the
module and DI wiring, typed payloads, attributes, lifecycle, logging and docs. Corvis does not carry its own copy of
the Lua scripts.

| Option | Interop evidence | Cost | Maintenance | Verdict |
|---|---|---|---|---|
| A. Wrap `bullmq-official` | 63/64 scripts identical to Node 6.7.2; upstream Node-parity tests (`rust/tests/*.rs`, 20 files) | Small: DI, attributes, typed jobs, docs | Upstream fixes scripts and logic; we follow releases | **Chosen** |
| B. Vendor the MIT Lua scripts, own client on `redis` | Same scripts, but the worker loop, locks, stalled check, retries and flows are ours to get right | Large: more than 9 000 lines in the upstream crate (`rust/src/*.rs`) to rewrite | We track every upstream script change by hand | Fallback if A fails |
| C. Implement the format without the scripts | None: loses atomicity, every state transition is a race | Large | Drifts at every release | Rejected |
| D. Third-party crate (`bullmq-rs` 2.2.0, by a single author) | Unverified | Small | Not maintained by the BullMQ authors | Rejected |

Corvis wraps instead of re-exporting: public types are `corvis::queues::{Queue, Job<T>, JobOptions, Backoff, ...}`,
so an upstream breaking change stays inside Corvis and `Job<T>` gets a typed payload (`T: DeserializeOwned`). Each
wrapper offers an escape hatch to the inner `bullmq` value (for example `Queue::inner()`) for features Corvis does
not wrap yet.

If a defect blocks a follow-up, first report it upstream; if upstream does not fix it in time, fall back to B for
that piece only (the scripts are MIT; keep the notice in a `THIRD_PARTY` file).

### 3. Redis client: the `redis` crate (redis-rs), through `bullmq-official`

The `redis` crate comes with option A (`ConnectionManager` for reconnection, `cluster-async`, rustls TLS). Corvis
does not add a second client. Later Redis features (cache store, throttler storage, WebSocket adapter, microservices
transport) should reuse the same crate and, where possible, the same connection options type.

- *`fred` 10.1.0:* good API, but its last release is from 2025-02-27 and it would put a second client in the tree
  next to the one `bullmq-official` needs.
- *Pools (`deadpool-redis`, `bb8-redis`):* not needed; the multiplexed `ConnectionManager` serves many tasks, and
  workers need dedicated blocking connections, which the crate opens itself.

### 4. Packaging: optional `queues` feature of `crates/corvis`, off by default

The module lives in `crates/corvis/src/queues/` behind `queues = ["dep:bullmq"]`, like `jwt` and `websockets`
(`crates/corvis/Cargo.toml:45-48`). The new handler kinds (`#[process]`, worker and queue event listeners) need to
live in `HandlerKind` (`crates/corvis/src/discovery.rs:61-67`) next to `WsMessage`, which is why a separate crate is
not proposed.

- *Separate `corvis-queues` crate:* keeps `corvis` lighter, but needs a public extension point for handler discovery
  that does not exist; a possible later refactor.
- *Always on:* would add `redis`, rustls and `croner` to every build. Rejected.

### 5. API shape (each follow-up refines it)

Close to `@nestjs/bullmq` so Node code ports line by line, with Rust types:

- `BullModule::for_root(BullRootOptions { connection, prefix, default_job_options })`, `for_root_async`, and
  `BullModule::register_queue(["emails"])` (#50). The connection accepts a URL or typed fields (host, port,
  username, password, db, TLS), matching the ioredis options Node users already have in their config.
- `#[inject_queue("emails")] queue: Queue` on `#[injectable]` fields (#50); `Queue::add(name, &data, opts)`,
  `Queue::add_bulk` (#51).
- `#[processor("emails", concurrency = 5)]` on a provider and `#[process]` / `#[process("welcome")]` methods inside
  `#[handlers]` (#52). `@nestjs/bullmq` has a single `process(job)` method per processor (it requires the class to
  extend `WorkerHost`, `bull.explorer.js:59-75`); Corvis adds per-name dispatch because the issue asks for
  `#[process]` and it removes the `match job.name` boilerplate. A catch-all `#[process]` keeps the single-method
  style available.
- `#[on_worker_event("completed")]` for local events and `#[queue_events_listener("emails")]` +
  `#[on_queue_event("completed")]` for cross-process events (#53).

The `BullModule` name follows the issue text; see Open questions.

### 6. Errors and outcomes of a `#[process]` method

The method returns `Result<R, E>` with `R: Serialize` stored as `returnvalue` (JSON) and `E: Display` stored as
`failedReason`. Corvis provides `JobError::unrecoverable(msg)` (no retry), `JobError::delay_until(ts)` and
`JobError::rate_limited(ms)`, mapped to the crate's `Error` variants. A panic inside a processor fails the job (with
`failedReason` from the panic message) and does not kill the worker. A payload that does not deserialize into `T`
fails the job as unrecoverable, with a message naming the type and the serde error: retrying cannot fix it.
`stacktrace` holds the error chain (`{:#}`) as a one-element array; Node writes JavaScript stacks there, so tests
compare its length, not its text.

### 7. Cron for job schedulers comes from the crate, verified against `cron-parser`

Job schedulers use whatever `bullmq-official` computes (croner). #54 adds a differential fixture: a set of patterns
and time zones (including seconds fields, `L`, `#`, DST changes in `America/Caracas`, `Europe/Madrid`, `America/New_York`)
whose next N run times are recorded from Node BullMQ 6.7.2 (`cron-parser 5.10.3`) and compared. Corvis's `cron`
port is not used because it reproduces a different library.

### 8. Interoperability tests: live Node BullMQ, shared Redis, normalized snapshots

- **Where:** `crates/corvis/tests/bullmq_interop.rs` (feature `queues`), with the Node side in
  `crates/corvis/tests/interop/bullmq/`: `package.json` pinning `bullmq` exactly (6.7.2, and 5.81.5 under an alias
  `bullmq5`), `package-lock.json`, and `driver.mjs`.
- **Driver:** a long-lived `node driver.mjs` process spoken to over stdin/stdout with one JSON command per line:
  `add`, `addBulk`, `upsertJobScheduler`, `addFlow`, `startWorker` (with a scripted outcome per job name: return a
  value, throw a message, throw `UnrecoverableError`, report progress steps, sleep, never finish), `stopWorker`,
  `listen` (QueueEvents), `pause`, `resume`, `getJob`. Replies are JSON lines. The Rust test owns the scenario and
  the clock (timeouts), so the same scenario runs with any mix of sides.
- **Matrix:** for each scenario, a reference run with Node producer + Node worker on queue `ref-<scenario>`, then
  Node→Corvis, Corvis→Node and Corvis→Corvis on their own queue names, all on one Redis database.
- **Comparison:** after each run, dump every key `<prefix>:<queue>:*` with its type and contents, and the events
  stream, then normalize: job ids from `INCR` kept, UUIDs and lock tokens replaced by placeholders, timestamps and
  scores replaced by their order, stream ids dropped, JSON fields (`data`, `opts`, `returnvalue`, `progress`,
  `parent`) compared parsed (JavaScript writes `1` where serde writes `1.0`), `stacktrace` compared by length, the
  `meta` fields `version`/`library` excluded (documented divergence). The normalized snapshot and the ordered list
  of `(event, jobId)` must equal the reference.
- **Environment:** `CORVIS_REDIS_URL` (default `redis://127.0.0.1:56379`) and `CORVIS_BULLMQ_NODE_DIR` (default the
  harness folder; needs `npm ci` run there). Without Redis or `node_modules` the tests print why and pass as
  skipped; `CORVIS_BULLMQ_REQUIRED=1` turns that into a failure (for CI). Each test uses its own prefix
  (`corvis-test-<random>`) and deletes its keys.
- **CI (#56):** Linux job with a `redis:7` service bound to `127.0.0.1:56379`, Node 22, `npm ci` in the harness
  folder, `cargo test -p corvis --features queues --test bullmq_interop` with `CORVIS_BULLMQ_REQUIRED=1`.
- **Unit tests** for the wrapper (option mapping, `Job<T>` deserialization, attribute expansion) run without Redis.

Each follow-up (#51–#55) adds its scenarios to this harness; #56 builds the harness first (Decision 10) and closes
the epic with the full matrix, including retries and failures.

- *Alternative: recorded oracles (like `res_express.oracle.mjs`).* Cannot catch races or cross-process effects;
  interop is about two processes sharing state. Used only for pure functions (backoff values, cron next runs).
- *Alternative: rely on upstream's tests.* They test the Rust SDK against itself on Node-compatible scripts, not the
  Corvis wrapper, its defaults and option mapping, or Node processes on the same queue.

## Risks / Trade-offs

- [Young upstream crate: 1.0 in July 2026, frequent releases] → pin a minor (`bullmq = { package =
  "bullmq-official", version = "~1.5" }`), bump on purpose with the interop suite, keep the public API in wrappers
  (Decision 2), and keep option B as the documented fallback.
- [Upstream changes the format again (a BullMQ 7)] → the suite pins the Node version; a bump shows any difference
  before release; docs name the supported major.
- [Mixed 5.x/6.x fleets pausing a queue can lose jobs (`RENAME` overwrite)] → docs warn; the 5.x interop subset
  excludes pause/resume; `Queue::pause` documents it.
- [Cron next-run times may differ from `cron-parser`] → differential fixture in #54; a pattern that differs is
  rejected at `upsert` with a clear error or listed in the docs, decided in #54.
- [Meta `library` vs `version` field divergence] → excluded from snapshot comparison; report upstream; if Node
  tooling relies on `meta.version`, Corvis can write it itself after the crate does (#50 decides).
- [Heavier dependency tree when `queues` is on: `redis` with rustls and cluster, `croner`, `rmp-serde`, duplicate
  `sha1`] → only with the feature; check build time and `cargo tree -d` in #50.
- [MSRV: `redis 1.x` needs Rust 1.88] → the workspace has no `rust-version`; record 1.88 as the minimum for the
  `queues` feature in #50.
- [Security: job payloads come from Redis, which other services also write] → `Job<T>` deserializes into a typed
  struct; malformed payloads fail the job without retry (Decision 6); `sizeLimit` honoured; connection passwords
  never logged (URLs redacted in logs and errors); `rediss://` supported. Lua runs inside Redis with the
  permissions of the connection; Corvis sends only the vendored upstream scripts.
- [Timing-sensitive interop tests (locks, stalled checks)] → scenarios set short `lockDuration`/`stalledInterval`,
  wait on events instead of sleeping, and compare order rather than time.

## Open questions

1. Is BullMQ 6.x the right primary target, or must the first release also guarantee pause/resume with 5.x
   processes? (Recommendation: 6.x primary, 5.x subset as above.)
2. Module name: `BullModule` (as in issue #50 and `@nestjs/bullmq`) or a neutral `QueueModule` with
   `BullModule` as an alias? The naming rule only bans "Nest"/"NestJS"/"Prisma", so `BullModule` is allowed; it
   eases porting.
3. Should `#[process("name")]` per-name dispatch be the documented default, or should the single `#[process]`
   method (closest to `WorkerHost.process`) be the documented default with per-name dispatch as an option? What
   happens to a job whose name has no handler and there is no catch-all: unrecoverable failure (proposed) or retry?
4. Is the interop suite required in CI for every pull request, or nightly plus on changes under
   `crates/corvis/src/queues/`? It needs Node and Redis on the Linux runner.
5. Should the Corvis wrapper write `meta.version` (Node's field) so Node tooling that reads `queue.getVersion()`
   keeps working, or leave the upstream crate's `library` field alone and report the divergence upstream?
6. Is a dependency on a crate pinned to `~1.5` that releases twice a week acceptable, or should Corvis vendor the
   crate's sources at a reviewed commit?
